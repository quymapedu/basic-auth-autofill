# Basic Auth Autofill — Chrome Extension Design

**Date:** 2026-07-27
**Status:** Approved, not yet implemented
**Location:** `browser-ext/` in the `ai-orchestrator` superproject

## Problem

`dev.mapedu.com` and `staging.mapedu.com` sit behind HTTP Basic auth enforced by a
CloudFront Function at the edge:

```
$ curl -I https://dev.mapedu.com/
HTTP/2 401
www-authenticate: Basic realm="Login"
x-cache: Error from cloudfront
```

HTTP Basic is stateless — there is no session or cookie, so every request must carry
an `Authorization` header. Chrome holds those credentials in memory only, keyed by
origin and realm, and drops them on browser restart, in a new profile, and in
incognito. The result is a sign-in dialog appearing repeatedly during normal work.

Chrome's password manager does not solve this. It keys HTTP-auth credentials by
`origin + realm` (here `https://dev.mapedu.com/Login`), but the "Add password" UI can
only create a plain `https://dev.mapedu.com/` entry, which never matches. Third-party
password managers cannot fill the dialog either — it is browser chrome, not page DOM.

An interim fix exists at `~/Developer/mapedu-dev-auth`: a static `declarativeNetRequest`
ruleset generated by a shell script, with credentials baked into `rules.json`. It works
but cannot be shared or published, because the credentials ship inside the package.

## Goals

- Attach `Authorization: Basic` to configured origins so the 401 never occurs.
- Manage an arbitrary number of sites, each with its own credentials, through a UI
  inside the extension.
- Ship no credentials in the package, so the extension is safe to share or publish.
- Verify a credential at the moment it is typed, rather than after hitting a broken page.

## Non-goals

- Replacing the server-side fix. Issuing a signed cookie from the CloudFront Function
  would remove the need for this extension entirely and is the better long-term
  answer; it is blocked on the dev/staging distributions not being managed in
  `terraform/` (that repo declares exactly one distribution, `status_page/main.tf:155`).
- Encrypting credentials at rest. See "Security posture".
- Any browser other than Chrome/Chromium.

## Key constraint

Manifest V3 removed blocking `webRequest` for non-enterprise extensions, so an
extension can no longer *answer* Chrome's auth prompt via `onAuthRequired`.
Pre-attaching the header with `declarativeNetRequest` is the only mechanism available.
Every approach below is a variation on that.

## Approach

**Chosen: `chrome.storage.local` is the source of truth; DNR dynamic rules are derived
from it.**

The options page writes site records to storage. The service worker observes
`storage.onChanged` and rebuilds the entire rule set. Dynamic rules are persistent, so
they survive browser restarts and apply while the service worker is asleep — DNR is
evaluated in the network stack, not in JavaScript.

Rejected alternatives:

- **Session rules** (`updateSessionRules`) keep credentials out of Chrome's on-disk rule
  store, but vanish on restart and must be rebuilt from `chrome.runtime.onStartup`.
  Restored tabs can issue requests before the worker finishes booting, producing exactly
  the 401 prompt this extension exists to remove. The security gain is illusory anyway,
  since `storage.local` is already unencrypted on disk.
- **DNR rules as the only store** removes sync logic but cannot represent a
  saved-but-disabled site, and forces the UI to base64-decode credentials out of a
  header to populate its own form.

The sync risk in the chosen approach is contained by treating the rule set as a pure
function of storage: read all sites, emit all rules, replace wholesale on every change.
Individual rules are never patched.

## Architecture

```
options.html/.js/.css   the manager UI (a tab)
      | writes
      v
chrome.storage.local    source of truth: sites[]
      | storage.onChanged
      v
background.js           service worker: rebuilds the whole rule set
      | uses
      v
lib/rules.js            pure: sites[] -> DNR rules[]   <- unit tested
      |
      v
chrome.declarativeNetRequest dynamic rules
```

| File | Responsibility | Depends on |
|---|---|---|
| `manifest.json` | MV3 declaration, permissions | — |
| `lib/rules.js` | `buildRules(sites) -> rules[]`, pure, no browser APIs | — |
| `lib/storage.js` | typed read/write accessors over `chrome.storage.local` | `chrome.storage` |
| `background.js` | rule sync, Test handler, toolbar click | `lib/*`, `chrome.declarativeNetRequest`, `chrome.permissions` |
| `options.html/.js/.css` | site list, add/edit/delete, Test, permission prompts | `lib/storage.js`, `chrome.permissions` |
| `icons/` | 16/48/128 px PNG | — |
| `README.md` | install, usage, manual test checklist, security note | — |

`lib/rules.js` imports nothing and touches no browser API, which is what makes it
testable under plain `node --test`.

## Data model

One record per site, stored in `chrome.storage.local` under the key `sites`:

```js
{
  id: string,        // crypto.randomUUID()
  origin: string,    // "https://dev.mapedu.com" — normalized, no trailing slash
  username: string,
  password: string,
  enabled: boolean
}
```

`origin` is the single field everything derives from:

| Derived value | Expression |
|---|---|
| Permission pattern | `` `${origin}/*` `` |
| Rule `urlFilter` | `` `|${origin}/` `` |
| Display name | `origin` |

Input is normalized through `new URL()`, defaulting a bare host to `https://`. So
`dev.mapedu.com`, `https://dev.mapedu.com`, and `https://dev.mapedu.com/courses/625`
all collapse to `https://dev.mapedu.com`. Duplicates are rejected inline.

## Rule generation

`buildRules(sites)` filters to entries that are `enabled` and have a non-empty
`username`, then emits one `modifyHeaders` rule per site with ids assigned by index:

```js
{
  id: index + 1,
  priority: 1,
  action: {
    type: "modifyHeaders",
    requestHeaders: [
      { header: "Authorization", operation: "set", value: `Basic ${token}` }
    ]
  },
  condition: {
    urlFilter: `|${site.origin}/`,
    resourceTypes: [
      "main_frame", "sub_frame", "stylesheet", "script", "image", "font",
      "object", "xmlhttprequest", "ping", "csp_report", "media",
      "websocket", "other"
    ]
  }
}
```

Two details that are easy to get wrong:

**UTF-8 before base64.** `btoa` throws a `InvalidCharacterError` on any code point above
U+00FF, so a password containing an accented character breaks encoding. RFC 7617
specifies UTF-8, so the token is:

```js
btoa(String.fromCharCode(...new TextEncoder().encode(`${username}:${password}`)))
```

**`|` anchoring.** `urlFilter: "|https://dev.mapedu.com/"` anchors at the start of the
URL, matching that exact host. Without the anchor, `dev.mapedu.com` would also match
`assets.dev.mapedu.com` and leak the credential to the CDN.

`resourceTypes` is listed explicitly rather than omitted, so `main_frame` is
unambiguously covered.

## Permission model

The manifest declares `optional_host_permissions` for `https://*/*` and `http://*/*`
rather than `host_permissions`. Install therefore shows no broad-access warning, and
each site is granted individually at the moment it is added.

**The user-gesture trap.** `chrome.permissions.request()` must be called from within the
click handler's synchronous call stack. Awaiting anything first — a storage read, an
async validation — discards the user gesture and Chrome rejects the call with
"This function must be called during a user gesture". The Add handler therefore:

1. Validates the form synchronously (URL parse, duplicate check against already-loaded
   state, non-empty username).
2. Calls `chrome.permissions.request({ origins: [`${origin}/*`] })` as the first async
   operation.
3. Writes to storage only after that resolves `true`.

Denied permission saves nothing and shows an inline explanation.

Rule emission is filtered in two stages, because `lib/rules.js` is pure and cannot call
browser APIs:

1. `background.js` drops sites whose host permission is not currently granted, checked
   via `chrome.permissions.contains`.
2. `buildRules()` drops sites that are disabled or have an empty username.

A site whose permission was later revoked through `chrome://extensions` remains in the
list but renders a **Grant** button rather than silently failing.

Deleting a site calls `chrome.permissions.remove` for its origin in addition to removing
the record.

## Test button

Each row has a Test button. The options page sends a message to the service worker via
`chrome.runtime.sendMessage`; the worker performs the fetch. This routing is deliberate:
MV3 is stricter about cross-origin fetches from extension pages, and the worker path is
unambiguous.

The worker builds the `Authorization` header explicitly rather than relying on the
installed DNR rule, so the test measures the credentials currently in the form rather
than whatever rule happens to be installed.

| Response | UI state |
|---|---|
| `2xx` or `3xx` | **ok** |
| `401` | **rejected** |
| network error / DNS failure | **unreachable** |
| any other status | shows the status code verbatim |

The request uses `method: "GET"`, `cache: "no-store"`, and `redirect: "manual"` so a
redirect to a login page is not followed and misreported as success.

## Error handling

| Condition | Handling |
|---|---|
| Unparseable URL | inline field error, nothing saved |
| Duplicate origin | inline field error naming the existing entry |
| Empty username | inline field error |
| Permission denied | inline row state with a retry button |
| Permission revoked externally | row shows **Grant**; no rule emitted |
| `updateDynamicRules` throws | banner at the top of the options page with the error text |

The `updateDynamicRules` failure case matters more than it looks: a silent failure is
indistinguishable from success until a 401 appears, so it must surface loudly.

## Security posture

Credentials are stored unencrypted in `chrome.storage.local`. Anyone with read access to
the Chrome profile directory can recover them. This is acceptable for shared
non-production environment passwords and is not acceptable for anything else. The
README states this directly.

The `Authorization` header is attached to every request matching a configured origin,
subresources included. Origin anchoring keeps it from reaching sibling subdomains.

No credentials exist anywhere in the repository or the packaged extension.

## Testing

**Unit — `node --test`, no dependencies.** `lib/rules.js` is pure, so it is covered
without a browser:

- empty site list produces an empty rule set
- disabled sites are excluded
- sites with an empty username are excluded
- ids are sequential from 1 and unique
- ASCII credentials produce the expected base64 token
- a password containing non-Latin-1 characters encodes as UTF-8 rather than throwing
- `urlFilter` is `|`-anchored and includes the trailing slash

**Manual — checklist in `README.md`,** covering what unit tests cannot:

1. Load unpacked; confirm install shows no broad host-access warning.
2. Add `https://dev.mapedu.com`; confirm Chrome prompts for that host only.
3. Load the site; confirm no auth dialog appears.
4. Change the password to a wrong value; confirm Test reports **rejected**.
5. Restore the password; confirm Test reports **ok**.
6. Disable the site; confirm the auth dialog returns.
7. Delete the site; confirm the permission disappears from `chrome://extensions`.
8. Restart Chrome; confirm the remaining sites still work with no prompt.
9. Add a second site with different credentials; confirm both work independently.

## Migration

`~/Developer/mapedu-dev-auth` is superseded. After the new extension is verified, remove
the old unpacked extension from `chrome://extensions` and delete the directory —
`rules.json` there contains live credentials in plaintext.

## Open decision: distribution

Not required for implementation, recorded so it is not lost.

Chrome Web Store registration is a one-time $5 developer fee. Public listing is
inappropriate — the extension is useless outside MapEDU. The viable options are
**Private/domain-restricted** visibility (requires a Workspace admin to enable
domain-restricted publishing), **Unlisted** (no Workspace setup, install by direct link),
or **no store at all** (force-install via Admin console policy, or load unpacked as
today). For a tool this size, load-unpacked is the proportionate default until the team
wants automatic updates.
